# i18n Audit: signals.gitdealflow.com locale tree (2026-08-15)

Triggered by the gitdealflow.com de/es cleanup (same day). Question: is the
pSEO site's 12-locale layer also fake-i18n that should be redirected to English?

## Verdict: HEALTHY. Keep it. Do not redirect. Do not "fix" lang either.

The landing site (gitdealflow.com) shipped ~414 English pages under
lang="de"/lang="es" with translated titles only — cosmetic i18n, killed via
catch-all 308s to English on 2026-08-15. The pSEO site's locale layer is a
fundamentally different, deliberate architecture that passes every check the
landing site failed.

## Architecture (source: content/locales.ts, content/locale-topics.ts)

- 12 locales: zh ja de es fr pt ko hi ru it nl ar (ar = RTL)
- 8 topics x 12 locales = 96 pages + 12 locale landings + 5 long-form
  Japanese research translations (/ja/research/<slug>)
- Content is HAND-WRITTEN per locale (documented quality bar: "a native
  speaker would not flag any sentence as MT slop"), NOT a machine-translated
  site mirror
- Each locale page links back to the English canonical; strategy comments
  explicitly reject thin/translated full-site copy

## Known deviation, deliberately NOT fixed

Locale pages render `<html lang="en">` (root layout hardcodes it) with
content inside a nested `<div lang={locale} dir={...}>`. This is valid
HTML — nearest-ancestor lang wins for crawlers and assistive tech — and
the impact is cosmetic. The "obvious" fixes are traps:

1. `headers()` in the root layout to read the locale -> forces dynamic
   rendering site-wide, defeats ISR (regression this project already
   fought; see skill nextjs-dynamic-rendering-defeats-isr).
2. Route-group refactor so [locale] renders its own <html> -> large
   structural change for negligible gain.
3. Rewriting the body in proxy.ts -> surgery on a load-bearing file
   (canonical 308s, X-Robots-Tag, markdown rewrite, bot_crawl analytics).

If the app ever moves to locale route groups for other reasons, set the
real <html lang> then. Until then, leave as-is.
